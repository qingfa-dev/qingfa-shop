# Payments Module Release

## What changed

- New `Payments` module across Core, Application, and Infrastructure with an event-sourced `Payment`
  aggregate, refunds, a capture ledger, and expiry.
- `IPaymentGateway` port with three adapters: `Fake` (deterministic, for local runs and tests),
  `Stripe` (Stripe.net), and `PayPal` (typed `HttpClient`).
- Customer routes under `/api/payments`, admin routes under `/api/admin/payments` gated by
  `payments.read`, `payments.manage`, and `payments.refund`.
- Signed webhooks at `POST /api/payments/webhooks/{provider}`, deduplicated per
  `(provider, provider_event_id)` and settled through the same command as the confirm return path.
- Projections and side tables in schema `payment`: `payments`, `payment_refunds`,
  `payment_webhook_events`, `payment_idempotency_keys`, `payment_references`.

## Behaviour worth knowing

- Every endpoint returns the existing `Result` / `Result<T>`; the HTTP status comes from
  `Result.StatusCode`.
- A provider decline at create is a `201` resource with `status = failed`; a decline at capture is
  `502 Payments.Provider.Declined` and leaves the authorization live.
- `Idempotency-Key` is required on create and refund. Replays return the stored resource with
  `Idempotent-Replay: true`; a reused key with a different body returns `409`. A create that fails
  after reserving the key releases the reservation so a retry works.
- Pending refunds reserve credit, so two pending full refunds cannot both succeed.
- Reads fall back to the event stream while a projection is catching up, so a payment is readable
  immediately after creation.
- Webhook amount mismatches are acknowledged with `200` and recorded as `AmountMismatch`; retries
  cannot fix them.
- Validation is owned by the domain and the endpoint edge: application slices have no validators, so
  a rejected request is always the documented `400`/`404`/`409` with a `Payments.*` code, never a
  generic `422`.
- Every failure comes from `PaymentsOutcome`; the catalogue has no unreachable codes.

## Configuration

`Payments:Providers:Fake` must be disabled in `Production`; startup validation enforces it.

Limits live in `Payments:Policy`: `MaximumAmountsByCurrency` (per ISO 4217 code),
`HostedCheckoutIntentLifetime`, and `ProviderExpiryGracePeriod`. A currency without an entry is rejected
with `Payments.Payment.CurrencyUnsupported`, and an amount above that currency's ceiling is rejected with
`Payments.Payment.AmountExceedsLimit`, both before any provider call.
Real providers require secrets from environment variables or user secrets — nothing is committed, and
an enabled provider without secrets fails fast at boot.

## Operational notes

- The gateway declares explicit `/api/payments/*` and `/api/admin/payments/*` routes before the
  `/api` catch-all; the webhook route is anonymous and both payment routes preserve `/api`.
- Messaging still defaults to `InMemory` outside AppHost/Compose, and no new backing service was
  added for payments.

## Known limitations

- PayPal refunds are implemented for full amounts and target the provider capture id
  (`v2/payments/captures/{id}/refund`); partial PayPal refunds still report
  `Payments.Refund.PartialUnsupported`.
- Disputes/chargebacks are accepted and recorded but do not change payment state.
- Reconciliation is opt-in (`Payments:Reconciliation:Enabled`, default `false`): a scheduled sweep re-reads
  stale unsettled payments and settles them through the same command the webhook uses.
- Webhook deliveries are pruned after `Payments:Retention:WebhookEventRetentionDays` (default 30) by a hosted
  worker that runs every `SweepIntervalHours` (default 6); only processed deliveries are eligible.
- `make test.payments.sandbox` runs live provider checks only when `STRIPE__SECRETKEY` or
  `PAYPAL__CLIENTSECRET` is set, and is never part of `make ci`.
