# Internationalization — Non-Functional Requirements

Per-store locales, default-locale fallback, currency display, and right-to-left behavior across
the storefront and admin front-ends.

**Links:** [Stores & i18n](../02-functional/12-stores-i18n.md) · [Performance](./01-performance.md) · [Requirements Index](../README.md) · [Spec](../../11-spec/README.md)

---

## Purpose

resys-eshop is multi-store and multi-locale. A `Store` declares a default locale and a set of
supported locales, and catalog presentation text is stored as per-locale rows using the
**`Translatable`** pattern (spec §6, `01/02-12`). The functional rules for locale selection,
fallback, and translation management live in FR-I18N-001 … FR-I18N-004; this file states the
quality attributes those rules must satisfy.

Two platform invariants bound i18n: money is always a strongly-typed
`(decimal, ISO-4217 currency)` value — never a raw decimal — and orders are priced in the store
currency for their whole lifecycle (spec §6, `01/02-12`). Locale resolution and formatting are
**server-side**; the clients render what the API returns. The i18n and money data model is owned
by `03/03-03`, and the storefront's `@nuxtjs/i18n` configuration is owned by `04/01-01`.

---

## NFR-I18N-001 — Per-store supported locales

- **Description:** Each store independently declares its default locale and the set of locales it
  supports, and the platform serves content only for that store's supported set (FR-STO-004,
  FR-I18N-002).
- **Target:** Locale is resolved per store, never globally; a store's supported-locale set is
  non-empty and validated against known locale tags; a request for a locale outside the set never
  renders content from another store's configuration.
- **Measurement:** Integration tests configure two stores with disjoint locale sets and assert
  each resolves only its own; store-settings validation tests reject an empty or invalid locale
  set; the configuration surface is reviewed in `03/03-02`.

---

## NFR-I18N-002 — Default-locale fallback

- **Description:** When a requested locale is unsupported, or a supported locale lacks a
  translation for a field, the platform falls back to the store's default locale instead of
  erroring or rendering an empty field (spec §6, FR-I18N-002).
- **Target:** Every translatable response field is non-empty for the resolved locale: a missing
  translation yields the default-locale value. The same fallback behavior is applied uniformly
  across browse, detail, and search responses and in the admin editing surface (FR-CAT-008,
  FR-I18N-003). Fallback is applied **before** the response leaves the server.
- **Measurement:** Integration tests request a supported-but-untranslated field and an
  unsupported locale and assert the default-locale value; a contract test asserts no empty
  translatable field is returned; the locale-matching algorithm is specified in `03/03-03`.

---

## NFR-I18N-003 — Locale-aware currency display

- **Description:** Prices and monetary amounts are always `Money` values of
  `(decimal, ISO-4217 currency)` and are formatted for display according to the resolved locale
  and the order/store currency (spec §6, FR-CAT-007, FR-STO-003).
- **Target:** No monetary value is transmitted or stored as a bare decimal; every response
  carries an ISO-4217 currency code alongside the amount; storefront and admin formatting uses
  locale-aware number/currency formatting (grouping, decimal separator, symbol placement) and
  never assumes a single currency symbol; a value in an unsupported currency is not sold or
  displayed as a selling price.
- **Measurement:** Contract tests assert the `Money` shape on catalog, cart, order, and admin
  responses; formatting unit tests cover multiple locales and currencies; a scan for raw decimal
  money fields is part of the schema review in `03/03-03`.

## NFR-I18N-004 — Right-to-left support

- **Description:** The platform must render correctly for right-to-left locales (for example
  `ar`, `he`) when a store enables them, even though the initial launch locale set may be
  left-to-right only.
- **Target:** The resolved locale sets the document direction (`dir="rtl"` for RTL locales);
  layouts use logical CSS properties (inline-start/inline-end) so they mirror without per-locale
  stylesheets; Tailwind CSS v4 logical utilities and PrimeVue direction support are used in the
  storefront and admin respectively; RTL is a configuration capability, not a code fork.
- **Measurement:** Visual/E2E checks render a representative RTL locale and assert mirrored
  layout and correct `dir`; component review in `04/01-03` and `04/02-03` confirms logical
  properties; the supported RTL locale list is configured per store.

---

## NFR-I18N-005 — Server-side locale resolution

- **Description:** The effective locale for a request is resolved on the server from the store's
  supported locales and the request's locale preference, so clients need no language logic and
  cannot override store configuration with a conflicting client parameter (FR-I18N-003).
- **Target:** Locale negotiation considers the request's `Accept-Language`/locale preference with
  quality weighting and falls back deterministically; a client-supplied locale that conflicts
  with the store's supported set is ignored rather than trusted; resolution is consistent across
  all public endpoints for a given request.
- **Measurement:** Integration tests send varied `Accept-Language` headers and assert the
  resolved locale; a contract test asserts browse, detail, and search resolve identically; the
  matching algorithm and fallback chain are finalized in `03/03-03`.

---

## NFR-I18N-006 — Localized dates, numbers, and messages

- **Description:** Beyond catalog text, user-facing dates, numbers, and validation/error messages
  are localized for the resolved locale so the experience is coherent.
- **Target:** Order dates, review dates, and numeric quantities are formatted per the resolved
  locale; validation and error messages returned by the API are localizable and rendered in the
  resolved locale where a translation exists, falling back to the default locale otherwise;
  machine-readable error codes remain stable regardless of locale.
- **Measurement:** Integration tests assert localized messages for at least two locales; error
  contract tests assert stable codes independent of the message text; the message catalog and
  fallback are reviewed with `03/03-03` and `04/01-01`.

## Open Questions

1. The exact locale-matching algorithm (Accept-Language parsing, quality weights, and the
   fallback chain) is finalized in `03/03-03`.
2. Which RTL locales, if any, are enabled at launch is a store-configuration decision; the
   platform capability is required regardless.
3. Whether customer accounts and store credit are shared across stores or kept per store is
   resolved with the multi-store model `03/03-02`.
4. The API error-message localization catalog and its integration with `@nuxtjs/i18n` are
   finalized in `03/03-03` and `04/01-01`.
