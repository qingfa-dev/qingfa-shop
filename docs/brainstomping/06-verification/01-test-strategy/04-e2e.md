## Purpose

End-to-end tests are the only layer that proves a user-visible journey through the built storefront
and admin against the real API. They run in `tests/Resys.E2E` on Playwright, are CI stage 5 in
`05/03-03`, and are the executable form of the journeys in `04/01-01` and `04/02-01`. They consume the
development seed dataset (`05/01-04`) rather than building fixtures, because a journey needs a
realistic catalog, tax, and promotion configuration to be meaningful.

The guiding rule: **an E2E test proves a journey, not a widget.** A pure formatting or state rule is
proven in the unit or component layer; E2E spends its cost on the path a shopper or an admin actually
walks.

## Playwright Projects

`tests/Resys.E2E` defines two Playwright projects so the two front-ends can run in parallel and be
filtered independently.

| Project | Target | Base URL | Auth |
|---|---|---|---|
| `storefront` | `web/storefront` | `http://localhost:3000` | Anonymous, or customer `storageState` |
| `admin` | `web/admin` | `http://localhost:3001` | Admin `storageState` (platform and store-scoped) |

- **Both projects run against the built apps**, served by `pnpm --filter <app> preview` after
  `build`, matching the CI commands in `05/03-03` stage 5.
- **`playwright.config.ts`** sets `baseURL` per project, `trace: 'on-first-retry'`,
  `screenshot: 'only-on-failure'`, `video: 'retain-on-failure'`, and `retries: 0` locally, `1` in CI.
- **A setup project authenticates once** and writes `storageState` files: a platform admin
  (`admin@resys.test`), a store-scoped admin (`eu-admin@resys.test`), and a customer
  (`shopper@resys.test`), using the seeded credentials from `05/01-04`. Journey specs reuse the state
  rather than logging in through the UI on every test.
- **Selectors are role- and test-id-based.** Specs prefer `getByRole` and a stable `data-testid` over
  text that changes with locale or copy. A missing test id is added to the component, not worked
  around with a brittle selector.

## Seeded-Dataset Requirement

The E2E stack is brought up exactly as CI does (`05/03-03` stage 5):

```bash
docker compose up -d
dotnet run --project src/Resys.Api -- migrate
dotnet run --project src/Resys.Api -- seed --profile demo
```

The suite depends on the demo dataset and keys off its stable natural identifiers (`05/01-04`):

| Need | Seeded source |
|---|---|
| Store resolution and locale | `resys-main` (`USD`, `en-US`) and `resys-eu` (`EUR`, `de-DE`). |
| Catalog and facets | The twelve products, option types, and variants; `classic-tee` has eight variants. |
| Stock states | At least one variant out of stock with backorders disabled. |
| Shipping, tax, promotions | `Flat Rate`/`Free Shipping`/`Expedited`; `US-CA` and `DE` rates; `WELCOME10`, `FREESHIP-75`, `SUMMER-CLOTHING`. |
| Accounts and roles | Platform admin, store-scoped admin, two customers. |
| Order states | One seeded order per state for admin list and fulfillment journeys. |

**A journey must not mutate a seeded record it does not own.** Read-only journeys (browse, listing,
product detail, admin list) use the seeded rows directly. A journey that writes (place an order,
create a product, adjust stock) creates its own uniquely named entity through the admin or public API
in its arrange step and cleans it up in teardown, so specs remain independent and re-runnable without
re-seeding. The suite never assumes execution order.

## Payment in E2E

The checkout journeys must be deterministic and hermetic, so E2E does not call a live Stripe or PayPal
sandbox on the blocking lane. The E2E environment registers a **`stub` `IPaymentGateway`** through the
extension seam (`03/02-07`) whose hosted step is a first-party test page returning a success or a
decline token. The store configures the `stub` gateway for E2E.

- Journey 1 uses the success token; Journey 2 uses the decline token to prove recovery.
- The card-data rule is still exercised: only a token crosses the wire, and the stub never receives a
  PAN (`FR-PAY-010`).
- A separate, non-blocking lane may run the real provider sandboxes for adapter conformance; it is not
  part of the required E2E stage. Provider contract details are `03/04-05`.

## Critical Journeys

### Storefront — `04/01-01`

| # | Journey | Spec assertions |
|---|---|---|
| SF-1 | Browse home → category → product → cart → delivery → payment → confirm → confirmation. | Store resolution from host; store-scoped listing; exactly one variant resolves; server-computed totals; `cart → awaiting_payment`; confirmation shows the order number and a queued email. |
| SF-2 | Guest checkout with account creation at confirm. | Guest order links to the new account without resetting the cart or totals. |
| SF-3 | Failed payment recovery. | A decline leaves cart, addresses, and delivery selection intact; retry creates a new attempt; confirm stays blocked until a success. |
| SF-4 | Register and sign in, profile, addresses, order history. | Access token refresh; own orders only; address snapshot onto the order. |
| SF-5 | Guest order lookup by number and email. | Correct pair returns the order; a wrong pair is a generic not-found. |
| SF-6 | Wishlist add and move-to-cart. | Item resolves live price and stock; move obeys catalog and stock rules. |
| SF-7 | Review submission and moderation. | Review enters `pending`, is hidden publicly, and the verified-purchase flag is server-computed. |
| SF-8 | Coupon apply and remove in the cart. | `WELCOME10` recomputes totals; removal restores the pre-coupon total. |

### Admin — `04/02-01`

| # | Journey | Spec assertions |
|---|---|---|
| AD-1 | Session boot, store switch, sign out. | `GET /api/admin/auth/session` gates the shell; `X-Store` is set for later calls; cookies cleared on sign out. |
| AD-2 | Product create and edit. | Default variant created in the same transaction; per-currency price set; one primary image; archive instead of delete when history references the product. |
| AD-3 | Order fulfillment: list → detail → fulfill/ship → refund/return. | Fulfill commits `on_hand` outflow and releases the reservation; state → `shipped`; `OrderShipped` outbox row; refund never exceeds captured minus prior refunds. |
| AD-4 | Inventory adjustment and transfer. | A compensating movement, never an edit; transfer is same-store only; over-transfer is `409`. |
| AD-5 | Shipping, tax, and promotion configuration. | Unknown calculator or action key is `422`; effective-dated rates; duplicate coupon code in a store is rejected. |
| AD-6 | Store switcher scope. | A store admin sees only assigned stores; a store-scoped admin receives `403` for platform-level routes. |
| AD-7 | User management. | Duplicate email is `409`; store assignment revokes authority immediately; no password hash or unnecessary PII is rendered. |

A journey that cannot be made deterministic is not added to the blocking lane; it is quarantined with
an owner and a tracking note, per the flakiness policy below.

## Browser Matrix and CI Mapping

- **Chromium is the required, blocking project on every pull request.** It is the browser the suite is
  developed against and the fastest signal.
- **Firefox and WebKit run on the scheduled nightly lane and on `main`.** A failure there blocks the
  release, not the pull request. This is the test-strategy answer to the browser-matrix question in
  `05/03-03`.
- **A mobile-viewport Chromium project** runs the storefront listing, product, and cart journeys to
  cover the responsive breakpoints in `04/01-04`.
- **Lighthouse CI** runs on the storefront home, listing, product, and cart routes and asserts the
  Core Web Vitals budgets in `01/03-01` (LCP, INP, CLS, TTFB). The budgets themselves are owned by
  `06/03-02`.
- **Artifacts on failure** — the Playwright trace, screenshot, and video, plus the Lighthouse report,
  are uploaded by the CI job (`05/03-03` stage 5).

## Determinism Rules

- **No `waitForTimeout`.** Use web-first assertions (`expect(locator).toBeVisible()`) that retry until
  the state is true; a fixed delay is the top cause of a flaky suite.
- **Wait on the network or the DOM, not on a timer.** A navigation waits for the route; a mutation
  waits for the response or the resulting UI state.
- **One journey per spec**, with a fresh browser context per test; no state leaks between specs.
- **Unique test data.** Writing specs generate a unique slug or email from the run id and clean up.
- **No dependence on seeded order.** A spec that needs an order in a specific state arranges it
  through the admin flow or the API, not by assuming a seeded row was untouched.
- **Flaky quarantine.** A spec that fails intermittently without a product defect is quarantined with
  an owner and an expiry, and is not silently skipped; the policy is recorded with the quality metrics
  in `06/03-01`. Risk R-12 in `02/03` is the tracked reason.
