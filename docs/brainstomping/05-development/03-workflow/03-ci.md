# Continuous Integration

The pipeline stages that gate every pull request — build, unit, integration, front-end checks, E2E, and documentation checks — with the command each stage runs.

## Purpose

This file defines the automated gate a change must pass before it can be reviewed and merged. It
lists the pipeline stages in order, the exact command each runs, and what a failure means. The
pipeline is the automated half of the Definition of Done in `00/02-01`; the human half is the review
in `00/02-03`. The local equivalents of every command are in `05/03-01`.

CI installs the same pinned toolchain as a workstation (`05/01-01`), so a local pass predicts a CI
pass: .NET SDK 10.0.x, Node.js LTS, pnpm 10.x, Docker with Compose v2, and PostgreSQL 18.

---

## Triggers and Required Checks

- Runs on every push to a branch with an open pull request and on every push to `main`.
- All stages below are **required checks**: the pull request cannot merge while any is red.
- A stage runs only if the earlier stages pass, except where noted, so the fastest signal comes
  first.
- The pipeline is cached per lockfile: `packages.lock.json` for .NET and `pnpm-lock.yaml` for the
  front-end. A lockfile change invalidates the cache.

---

## Stage Overview

| # | Stage | Runs | Gate |
|---|---|---|---|
| 1 | Build and format | `dotnet restore` → `dotnet build -c Release` → `dotnet format --verify-no-changes`; `pnpm install --frozen-lockfile` | Compiler and formatter clean. |
| 2 | Unit tests | `dotnet test tests/Resys.UnitTests` | All unit tests pass. |
| 3 | Integration tests | `dotnet test tests/Resys.IntegrationTests` (Testcontainers PostgreSQL 18) | All integration tests pass. |
| 4 | Front-end lint and typecheck | `pnpm --filter … lint` / `… typecheck` for both apps | No lint error and no type error. |
| 5 | End-to-end | Playwright against the running stack in `tests/Resys.E2E` | All browser journeys pass. |
| 6 | Documentation checks | Forbidden-token scan plus the links-scoped check | No forbidden token and no broken link. |

Stages 2–5 depend on the artifacts from stage 1; they do not re-restore or re-build the solution.

---

## Stage 1 — Build and Format

Restore, compile in the release configuration, and enforce formatting. Warnings are errors
(`TreatWarningsAsErrors`, `05/02-01`).

```bash
dotnet restore Resys.sln
dotnet build Resys.sln --no-restore -c Release
dotnet format Resys.sln --verify-no-changes --severity warn
```

The build also emits the OpenAPI documents to `artifacts/openapi/` (`03/04-04`).

Install the front-end workspace with the frozen lockfile so CI never resolves a new version:

```bash
cd web
pnpm install --frozen-lockfile
```

A failure here is a compile error, a warning promoted to an error, or a formatting drift. Run
`dotnet format Resys.sln` locally to fix formatting (`05/02-01`).

---

## Stage 2 — Unit Tests

```bash
dotnet test tests/Resys.UnitTests -c Release --no-build
```

Covers domain units and architecture-boundary rules (`03/02-02`): an entity invariant, an engine
calculation, or a project reference that would violate the module boundary. No Docker and no network
are required. The test strategy and coverage expectations are owned by `06/01-01`.

---

## Stage 3 — Integration Tests

```bash
dotnet test tests/Resys.IntegrationTests -c Release --no-build
```

These tests use **Testcontainers** to start a disposable **PostgreSQL 18** instance, apply the
module migrations (`03/03-04`), and exercise the API host and persistence against a real database.
The CI runner therefore needs a working Docker engine; the socket is exposed to the job. Using the
same PostgreSQL major version as local (`05/01-03`) and production is the point of the stage: it is
where EF Core mappings, migrations, and store scoping are proven.

---

## Stage 4 — Front-End Lint and Typecheck

Run from `web/`:

```bash
cd web
pnpm --filter storefront lint
pnpm --filter storefront typecheck
pnpm --filter admin lint
pnpm --filter admin typecheck
```

- **Typecheck** enforces TypeScript strict in both apps and fails on `any` leaks and unresolvable
  imports (`05/02-03`).
- **Lint** runs the Nuxt/Vue ESLint configuration; a disabled rule must be scoped to a line with a
  reason (`05/02-03`).
- The generated OpenAPI client in `web/shared` is produced before this stage so its types are
  available to the typechecker (`03/04-04`).

---

## Stage 5 — End-to-End (Playwright)

The E2E project runs real browser journeys against the running system. The job brings the whole
stack up first:

```bash
# database + schema + demo data
docker compose up -d
dotnet run --project src/Resys.Api -- migrate
dotnet run --project src/Resys.Api -- seed --profile demo

# API host (Release, matching the Stage 1 build)
ASPNETCORE_ENVIRONMENT=Development dotnet run --project src/Resys.Api -c Release --no-build &

# built front-ends; each chain is backgrounded as a group
cd web
( pnpm --filter storefront build && pnpm --filter storefront preview ) &
( pnpm --filter admin build && pnpm --filter admin preview ) &
```

Then install the browsers and run the suite:

```bash
pwsh tests/Resys.E2E/bin/Release/net10.0/playwright.ps1 install --with-deps
dotnet test tests/Resys.E2E -c Release --no-build
```

The journeys cover the storefront and admin surfaces; the exact specs, browser matrix, and fixtures
are owned by `06/01-04`. A failure here means a user-visible flow broke, so the job uploads the
Playwright traces and screenshots as CI artifacts for debugging.

## Stage 6 — Documentation Checks

Documentation is a first-class deliverable (`00/02-01`), so the pipeline enforces the two checks
from §12 of the [design spec](../../11-spec/README.md): no
forbidden token and no broken relative link.

**Forbidden-token scan.** The pattern is inlined so the stage needs no external file, and it uses
character classes (`T[B]D`) so the command's own source text does not match the pattern. It scans
only the deliverable areas `docs/00`–`docs/10`, never `docs/11-spec/`:

```bash
grep -rnE 'T[B]D|TO[D]O|FIX[M]E|XX[X]|PLACE[H]OLDER|fill in the det[a]ils|implement lat[e]r' \
  docs/00-governance docs/01-requirements docs/02-planning docs/03-architecture \
  docs/04-design docs/05-development docs/06-verification docs/07-release \
  docs/08-operations docs/09-user docs/10-maintenance
```

`grep` exits `0` on a match, `1` when nothing matches (clean), and `2` when it cannot run. The stage
fails on exit `0` (a forbidden token) and on any exit other than `0` or `1` (the scan could not
run); only exit `1` is green. The pattern covers to-be-determined notes, action-item comments,
fix-me notes, the upper-case placeholder word, and the two deferral phrases. Genuinely undecided
work belongs under an explicit `## Open Questions` section (`00/02-01`).

**Links-scoped check.** Every relative markdown link between docs must resolve; plain-text
`AA/BB-CC` citations are used for files that do not exist yet:

```bash
find docs -name '*.md' -not -path 'docs/11-spec/*' -print0 | while IFS= read -r -d '' f; do
  grep -oE '\]\([^)]+\)' "$f" | sed -E 's/^\]\(//; s/\)$//' \
    | grep -E '\.md(#|$)' | grep -vE '^https?://' \
    | while IFS= read -r l; do
        t="$(dirname "$f")/${l%%#*}"
        [ -e "$t" ] || echo "BROKEN: $f -> $l"
      done
done
```

Any `BROKEN:` line fails the job. `http(s)://` links are skipped by the check; only repository
links are verified.

## Failure Handling

- **Stage 1 fails** — fix the compile error, warning, or formatting drift; do not disable an
  analyzer to get green.
- **Stage 2 or 3 fails** — the change is incorrect; a red test is never merged or skipped.
- **Stage 4 fails** — fix the lint or type error rather than suppressing it.
- **Stage 5 fails** — read the uploaded trace; reproduce locally with the running stack.
- **Stage 6 fails** — remove the forbidden marker or repair the link; the review policy requires
  this evidence before approval (`00/02-03`).

A red pipeline is necessary but not sufficient grounds for approval: reviewers must not approve on
the basis of CI alone (`00/02-03`).

## Reproducing CI Locally

Run the same commands from the repository root before pushing. `05/03-01` has the full local
command reference; the short version is:

```bash
dotnet restore Resys.sln
dotnet build Resys.sln --no-restore -c Release
dotnet format Resys.sln --verify-no-changes --severity warn
dotnet test tests/Resys.UnitTests -c Release
dotnet test tests/Resys.IntegrationTests -c Release

cd web
pnpm install --frozen-lockfile
pnpm --filter storefront lint && pnpm --filter storefront typecheck
pnpm --filter admin lint && pnpm --filter admin typecheck
```

Because CI pins the same versions as `05/01-01`, a green local run is strong evidence of a green CI
run.

## Open Questions

1. The CI provider and the job/workflow file layout are not fixed by this file; the stage order,
   commands, and required-check behaviour are the contract, and the workflow file implements them.
2. The forbidden-token pattern is inlined in the documentation-check stage; if the list grows,
   extracting it to a committed config file is a pipeline-scaffold decision, with the inline pattern
   in §12 of the spec and the review policy as the source of truth until then.
3. Whether the E2E stage runs the full browser matrix on every pull request or on a schedule is a
   test-strategy choice owned by `06/01-04`; the stage is required and blocking.
