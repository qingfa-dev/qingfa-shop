# C4 Model — Context, Containers, Components

The three C4 levels for resys-eshop: who uses it (context), what runs (containers), and how the API is composed internally (components).

**Links:** [App topology](./02-app-topology.md) · [Data flow](./03-data-flow.md) · [Architecture index](../README.md) · [Spec](../../11-spec/README.md)

---

## Purpose

This file orients a reader before they open the detailed architecture files. It uses the
[C4 model](https://c4model.com) conventions — context, containers, components — to show the
system at three zoom levels:

- **Level 1 — System Context:** the platform as one box, its human actors, and the external
  providers it depends on.
- **Level 2 — Containers:** the deployable/runtime units — the API service, the two Nuxt apps,
  PostgreSQL, object storage, and email — and how they talk.
- **Level 3 — Components:** the internal composition of the API service, namely the commerce
  modules wired together in one process.

Deeper material lives in sibling and child files: the project tree and module contracts are
`03/02-01` and `03/02-02`; the order state machine is `03/02-03`; the data model is `03/03-01`;
the REST surface is `03/04-01` and `03/04-02`. Deployment and runtime topology are `03/01-02`
and `08/01-01`.

## Level 1 — System Context

resys-eshop is a **multi-store, headless commerce platform**. Shoppers and administrators never
touch the commerce core directly; they use browser clients that call a REST API. The platform
depends on external providers for payment authorization, transactional email, and binary asset
storage.

```
        ┌───────────────┐                 ┌──────────────────────────────┐
        │   Customer    │  HTTPS (browser)│                              │
        │ (public user) │────────────────►│                              │
        └───────────────┘                 │                              │
                                          │         resys-eshop          │
        ┌───────────────┐                 │   (modular-monolith .NET     │
        │  Store Admin /│  HTTPS (browser)│     service + two Nuxt 4     │
        │ Platform Admin│────────────────►│     front-ends)              │
        └───────────────┘                 │                              │
                                          └───────┬───────────┬──────────┘
                                                  │           │
                         ┌────────────────────────┘           └───────────────┐
                         ▼                                                    ▼
            ┌────────────────────────┐                        ┌────────────────────────┐
            │  Payment providers     │                        │  Email provider        │
            │  Stripe · PayPal       │                        │  SES / SMTP            │
            └────────────────────────┘                        └────────────────────────┘
                         ▲
                         │
            ┌────────────────────────┐
            │  Object storage        │
            │  S3-compatible / disk  │
            └────────────────────────┘
```

**Actors**

| Actor | Description | Primary surface |
|---|---|---|
| Customer | Unauthenticated visitor or registered `customer`; browses, buys, manages orders/addresses/wishlists, writes reviews. | `web/storefront` |
| Store Admin | `admin` scoped to one or more stores; manages catalog, orders, inventory, pricing, shipping/tax/promotion config for assigned stores. | `web/admin` |
| Platform Admin | `admin` with platform-wide scope; manages stores, currencies, locales, users/roles, global settings. | `web/admin` |
| System | Background processing inside the API process: outbox relay, email dispatch, analytics stub. | none (in-process) |

**External providers**

| Provider | Purpose | Boundary |
|---|---|---|
| Stripe | Card payments; card data captured by Stripe Elements in the browser. | `IPaymentGateway` adapter (`03/04-05`) |
| PayPal | Alternative payments; card data captured by the PayPal JS SDK. | `IPaymentGateway` adapter (`03/04-05`) |
| Email (SES/SMTP) | Transactional email: order confirmation, payment receipt, shipment, return status. | `IEmailSender` (`03/04-06`) |
| Object storage (S3-compatible or local disk) | Product images and uploaded assets. | `IFileStorage` (`03/04-06`) |

The platform is **headless**: no in-process UI. Both front-ends are ordinary HTTP clients of the
same API. There is **no CMS, no GraphQL, and no recommendation engine**; those are explicitly out
of scope (ADR 0003).

## Level 2 — Containers

A "container" is a separately runnable or deployable unit. resys-eshop has three application
containers, one database, and two external infrastructure dependencies.

| Container | Technology | Responsibility |
|---|---|---|
| API service | ASP.NET Core Minimal API on .NET 10 (`Resys.Api`) | Exposes `/api/v1` (public) and `/api/admin` (back-office), runs the commerce modules, owns the database schema and outbox. |
| Storefront | Nuxt 4 SSR (Vue 3.5.43) | Public, SEO-oriented storefront: browse, search, cart, 3-step checkout, account, reviews. |
| Admin | Nuxt 4 + PrimeVue 4 | Back-office: catalog, orders, inventory, shipping/tax/promotions, store settings, users/roles, reports. |
| Database | PostgreSQL 18 via EF Core 10 / Npgsql | Single physical database with logical module ownership; stores all commerce state plus the outbox. |
| Object storage | S3-compatible bucket (local disk in dev) | Product images and assets served to the front-ends; the API holds signed references, not blobs. |
| Email provider | SES or SMTP relay | Delivers transactional email triggered by domain events. |

`web/shared` is a TypeScript library (API client, DTO mirrors, components, formatting) and is not
a container. `Resys.Shared` is a build-time contracts assembly and is not a container.

```
┌──────────────────┐        /api/v1        ┌─────────────────────────────────────┐
│ web/storefront   │──────────────────────►│            Resys.Api                 │
│ Nuxt 4 SSR :3000 │                       │   Minimal API on .NET 10             │
└──────────────────┘                       │   /api/v1     +     /api/admin       │
┌──────────────────┐        /api/admin     │   ┌───────────────────────────────┐  │
│ web/admin        │──────────────────────►│   │  12 commerce modules + Core   │  │
│ Nuxt 4 :3001     │                       │   └───────────────────────────────┘  │
└──────────────────┘                       └───┬───────────┬───────────┬──────────┘
                                               │           │           │
                                               ▼           ▼           ▼
                                      ┌─────────────┐ ┌──────────┐ ┌──────────────┐
                                      │ PostgreSQL  │ │ Object   │ │ Email        │
                                      │ 18   :5432  │ │ storage  │ │ (SES/SMTP)   │
                                      └─────────────┘ └──────────┘ └──────────────┘
```

**Container interaction rules**

- Only `Resys.Api` talks to PostgreSQL, object storage, email, and payment providers. The Nuxt
  apps never hold database credentials or provider secrets.
- The storefront uses the public `/api/v1` surface only; the admin app uses `/api/admin` only
  (ADR 0004). Both are unprivileged HTTP clients.
- Cart and checkout state live server-side in the database, not in the browser, so totals, tax,
  and promotions are always server-computed.
- Images are uploaded through the API and stored in object storage; clients receive a URL or a
  signed reference.
- Email is never sent inline on the request thread; events are persisted to the outbox and the
  relay dispatches them after commit.

## Level 3 — Components

Level 3 opens the API service. Internally it is a **modular monolith**: one process, one
database, but explicit module boundaries. Every module owns its entities, EF Core configuration,
services, and endpoints, and communicates with other modules through contracts and domain events
rather than by reaching into their internals (`03/02-02`).

**Commerce modules (12)**

| Module | Project | Owns |
|---|---|---|
| Catalog | `Resys.Modules.Catalog` | Products (master + variations), option types/values, taxonomy, images, per-locale text, price sets. |
| Orders | `Resys.Modules.Orders` | Order aggregate, line items, addresses, adjustments, the order state machine, checkout steps. |
| Inventory | `Resys.Modules.Inventory` | Stock items per (variant, location), reservations, stock movement ledger, backorder policy. |
| Shipping | `Resys.Modules.Shipping` | Shipping methods/calculators, zones, delivery selection, shipping adjustments. |
| Tax | `Resys.Modules.Tax` | Jurisdiction hierarchy, tax rates/categories, inclusive/exclusive computation. |
| Promotions | `Resys.Modules.Promotions` | Promotions, rules (coupon/user/product/order total/shipping), actions, adjustment output. |
| Payments | `Resys.Modules.Payments` | Payment records/attempts, gateway orchestration, refunds, reconciliation. |
| Returns | `Resys.Modules.Returns` | Return authorizations, return items, refund linkage, restock. |
| Wishlists | `Resys.Modules.Wishlists` | Named wishlists and their items for a customer. |
| Reviews | `Resys.Modules.Reviews` | Product reviews, ratings, moderation state. |
| Accounts | `Resys.Modules.Accounts` | ASP.NET Identity users, roles, addresses, per-store admin assignment. |
| Stores | `Resys.Modules.Stores` | Store records, domain mapping, currencies, locales, checkout options. |

**Supporting components**

| Component | Responsibility |
|---|---|
| Shared kernel (`Resys.Core`) | `Money`, identities, store-scoping primitives, domain-event types, extension contracts (`IShippingCalculator`, `IPaymentGateway`, `IPromotionAction`, `ITaxZoneResolver`, `OrderStateHooks`). Depends on nothing else in the solution. |
| Contracts (`Resys.Shared`) | DTOs and API contracts shared with clients; no domain logic. |
| API host (`Resys.Api`) | Minimal API endpoints for both surfaces, DI composition, auth, OpenAPI/Scalar, health checks. |
| Infrastructure (`Resys.Infrastructure`) | EF Core + Npgsql, ASP.NET Identity stores, `IFileStorage`, `IEmailSender`, gateway adapters, the outbox relay and event dispatcher. |

```
                    ┌───────────────────── Resys.Api (host) ─────────────────────┐
                    │  /api/v1 endpoints        /api/admin endpoints            │
                    └───────┬───────────────────────────┬───────────────────────┘
                            │                           │
        ┌───────────────────┴───────────┐   ┌───────────┴────────────────────────┐
        │        Commerce modules        │   │        Cross-cutting services      │
        │  Catalog   Orders   Inventory  │   │  Event dispatcher · Outbox relay   │
        │  Shipping  Tax      Payments   │   │  Auth/roles · OpenAPI/Scalar       │
        │  Promotions Returns Wishlists  │   │  Health checks · Request-id        │
        │  Reviews   Accounts  Stores    │   └────────────────────────────────────┘
        └───────────────┬────────────────┘                    │
                        │ contracts + events                   │
                        ▼                                      ▼
                ┌────────────────────┐              ┌────────────────────────┐
                │     Resys.Core     │              │  Resys.Infrastructure  │
                │  kernel/contracts  │              │  EF Core · Postgres    │
                └────────────────────┘              │  Identity · storage    │
                                                    │  email · gateways      │
                                                    └────────────────────────┘
```

**Component interaction rules**

- Dependency direction is one-way: modules depend on `Resys.Core`; `Resys.Infrastructure`
  implements `Resys.Core` contracts; `Resys.Api` composes modules and infrastructure. `Core`
  depends on nothing (`03/02-01`).
- A module never references another module's entities or `DbContext`; cross-module reads and
  writes flow through published contracts, and cross-module side effects flow through domain
  events.
- State transitions are the only status mutators. Each transition emits a domain event written to
  the outbox in the same transaction (`03/03-01`, `03/01-03`).
- Extension behaviour is added by implementing a `Resys.Core` contract and registering it in DI;
  no core source is modified, and resolution is last-registered-wins (`03/02-07`).

## Cross-Level Notes

- **Multi-store at every level.** At Level 1 a store is a tenant; at Level 2 it determines which
  catalog and configuration the API returns; at Level 3 it scopes every catalog, inventory,
  payment, and order row and gates admin access.
- **Multi-currency.** `Money` is a `(decimal, ISO-4217 currency)` value object; variants carry
  per-store price sets and orders are always priced in the store currency. There are no raw
  decimals in the model.
- **Stateless API, stateful database.** The API containers can scale horizontally; shared state
  lives in PostgreSQL and object storage, so no sticky sessions are required.
